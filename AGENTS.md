# AGENTS.md

This file provides guidance to agents when working with code in this repository.

- This repo is a static browser wallet: there is no root [`package.json`](package.json) and no build step. It does now have an automated proof harness — run [`tests/harness/run-all.sh`](tests/harness/run-all.sh) (after `npm install` in `tests/harness/`) before and after any change to the wallet, chain, or OTC code. It drives the real unmodified app in headless Chromium against mock chains that independently re-verify every broadcast, and covers happy / ROD-refund / alt-refund / reload scenarios on every supported counter chain. A change that keeps all suites green is very unlikely to have broken settlement; a change that cannot be exercised by it deserves a new scenario rather than a manual click-through.
- [`tests/harness/unit-browser-test.js`](tests/harness/unit-browser-test.js) is the fast gate (seconds, not minutes) for chain constants, fee/dust policy, and protocol invariants. Add to it before reaching for the full e2e matrix.
- Runtime depends on script-tag order in [`index.html`](index.html): crypto/libs load before [`js/coin.js`](js/coin.js), and [`js/coin.js`](js/coin.js) loads before [`js/coinbin.js`](js/coinbin.js). Do not convert to deferred/reordered loading without rechecking all globals.
- Network defaults are hard-coded in [`js/coin.js`](js/coin.js) `coinjs.networks`: ROD (mainnet prefixes, Bech32 HRP `rod`, API base `https://api.spacexpanse.org:1234`), LTC, DOGE, BTC, and BCH. BTC and BCH deliberately share Bitcoin's original version bytes (pub `0x00`, script `0x05`), so their legacy addresses are byte-identical; that is safe only because `terms.altChain` is inside the hashed canonical terms, and any new code that identifies a chain BY ADDRESS SHAPE rather than by chain code will be wrong for this pair. Wallet/explorer behavior assumes these defaults unless the Settings tab changes them at runtime; `engine.applyApiConfig()` is what propagates saved per-chain API bases and backend types back into these profiles.
- The wallet is intentionally offline-first but not fully offline: address generation/signing are local, while balance, UTXO, tx lookup, broadcast, and API health depend on the ROD API wrappers in [`coinjs.addressBalance()`](js/coin.js:419), [`coinjs.transaction().listUnspent()`](js/coin.js:1197), [`coinjs.transaction().getTransaction()`](js/coin.js:1239), and [`coinjs.transaction().broadcast()`](js/coin.js:1322).
- Broadcast and lookup handlers expect JSON-RPC-style `{result,error}` envelopes from the ROD API, not legacy Coinb.in/Chain.so payloads; preserve that normalization when editing API code.
- Wallet login compatibility is deliberate: deterministic open-wallet derivation in [`#openBtn`](js/coinbin.js:137) must remain stable for existing users, even though the flow is labeled less secure.
- SegWit support is intentionally split: new-address tools expose SegWit/Bech32, but the wallet access flow hides those controls in [`index.html`](index.html) and forces legacy by default in [`syncWalletSegwitState()`](js/coinbin.js:250) startup wiring for current API compatibility. Separately, Dogecoin has **no SegWit at all** — `coinjs.supportsSegwit()` returns false for it, the SegWit controls are hidden, `getWalletAddressType()` forces legacy, and [`chainsModule.publicKeyToAddress()`](js/otc-chains.js) throws rather than mint a `doge1…` address nothing would accept.
- Multi-chain rules live in exactly two places and should stay there. [`js/otc-chains.js`](js/otc-chains.js) owns version bytes and the relay policy table (fee rate, hard/soft dust, dust surcharge, change threshold, block spacing); [`js/otc-explorer.js`](js/otc-explorer.js) owns the block-explorer adapter that normalises Esplora (LTC, BTC), BlockCypher (DOGE) and Blockchair (BCH) into one Esplora-shaped response. Adding a chain should mean adding a `coinjs.networks` profile, a chain definition, a policy row, and a default in `engine.defaults.altChains`, and a fee row in `SWAP.ALT_CHAIN_FEES` — not new branches in the swap logic. `CHAINS.getPolicy()` and `SWAP.altFees()` both THROW on an unregistered chain rather than defaulting; that is deliberate, because a plausible-looking default fee or dust limit produces transactions that are unminable rather than obviously broken.
- The counter leg is generic ("alt"), not Litecoin. `terms.altChain` is part of the hashed canonical terms, so it binds the chain to every signature. Never call a chain helper with a literal `'LTC'` in swap code — read `altChainOf(session)` (UI) or `terms.altChain`. `engine.getAltHeight()` and `engine.altChainConfig()` both take a chain code; calling them unqualified silently targets the default chain, which is exactly the bug the DOGE alt-refund scenario was written to catch.
- Refund safety is a **wall-clock** relationship, not a block count: the alt leg's refund must mature before the ROD leg's, or the secret holder could reclaim ROD and still claim the alt coin. Each chain expresses that window in its own block count (LTC 24 × 2.5 min, DOGE 60 × 1 min, BTC and BCH 6 × 10 min, all ≈ 1 h against ROD's 480 × 30 s ≈ 4 h). The unit harness asserts this in seconds; do not add a chain by copying another chain's block count.
- Fee guidance is local-only in this fork. Keep the relay-floor logic centered on [`ensureWalletFeeMeetsRelayFloor()`](js/coinbin.js:463) and the offline estimate in [`feeStats()`](js/coinbin.js:2369); do not reintroduce remote fee estimators.
- Developer donation is intentionally disabled by default: [`coinjs.developer`](js/coin.js:22) is empty and [`#developerDonation`](index.html) defaults to `0`. Guard any donation-related change against emitting invalid outputs.
- Be careful when changing scripts or assets used by the PWA shell: update the cache list in [`sw.js`](sw.js) (and bump `STATIC_CACHE_VERSION`) and keep CSP/connect restrictions aligned in [`_headers`](_headers) — a new explorer backend needs its host added to `connect-src` or every request from the deployed PWA fails silently.
- Existing project history in [`CHANGELOG.md`](CHANGELOG.md) is the best source for non-obvious compatibility constraints and previously verified wallet behavior.
- **Peer messages are evidence of nothing.** Every Nostr handler in [`js/otc-app-ui.js`](js/otc-app-ui.js) must call `ensureRemotePeer()` before touching session state, and [`nostrModule.validateEnvelope()`](js/otc-nostr.js) now REQUIRES a signature (`event.id` is a plain hash anyone can recompute, so an unsigned event let a stranger impersonate the pinned counterparty). State that stops automation — `COMPLETE`, `declined`, "already refunded", "already claimed" — may only be set from locally verified chain facts, never from a message. Remote-sourced evidence is tagged `remoteOnly: true` and every refund gate ignores it. A message that could turn off the refund monitor is a total-loss bug, not a UX bug.
- Refund monitoring must OUTLIVE terminal states: `autoContinueSwap()` still calls `checkRefunds()` when `refundStillOwed()` holds, because both `COMPLETE` and `declined` are reachable from a counterparty message. Alice also refuses to start an alt claim once `refundRodHeight` is reached, so the claim path and the refund path can never both be in flight.
- A terms-hash mismatch on incoming terms is fatal except for one whitelisted difference: `sellerSwapXpub` / `buyerSwapXpub`, because a locally derived xpub is not byte-stable against the peer's published one even when both derive identical child keys. `canonicalTermsDiff()` proves nothing else differs. Do not widen that whitelist — every other field is economically material and none of them are protected by the hash comparison itself.
- Peer-supplied numbers that ride inside the hashed terms are NOT validated by the hash (the local rebuild reuses the same number, so the hash matches by construction). Settlement fees are floored against `SWAP.DEFAULT_FEES` / `SWAP.altFees()`, and `refundRodHeight` is floored against this client's own configured `refundRodBlocks`. Any new terms field a peer can influence needs the same treatment.
- ROD settlement fees are `0.00071000`, not the old `0.00051900`. A claim or refund spends a 2-of-2 P2SH output (~306 bytes); at ROD's ~232 sat/B floor that needs 70,992 sats. The old value was sized for the ~226-byte P2PKH FUNDING transaction and sat at 169 sat/B — under the relay floor, and `ROD.relayFloorPerByte` is 0 so nothing rejected it. Funding is separately `0.00053000`. The e2e harness pins these in `ROD_CLAIM_FEE` / `ROD_REFUND_FEE`.
- A broadcast txid is a hash of bytes we already hold. Never adopt the txid an explorer returns — compare it to the locally computed one and reject on mismatch. Recording claim/refund evidence from an API's word is what lets a hostile or merely broken backend suppress a refund.
- **BCH uses a different sighash and it is selected by the network profile, not by the caller.** Bitcoin Cash removed SegWit and replaced the legacy sighash with a BIP-143 preimage carrying a mandatory `SIGHASH_FORKID` (0x40) bit, so `'BCH'` in `coinjs.networks` sets `forkId: true` and every signing/verification path goes through [`transactionHashAny()`](js/coin.js) — never `transactionHash()` and never a literal `1` for the hash type. Use `tx.sigHashType()` for the trailing scriptSig byte too (`engine.completeSig` takes it as an argument). `transactionHashAny()` THROWS rather than falling back to the legacy algorithm: a silent fallback produces a signature both peers verify happily and the network rejects, which on a swap is a missed refund deadline.
- The fork-id preimage commits to the PREVOUT VALUE, which the legacy algorithm never needed. `addinput(txid, index, script, sequence, value)` takes it and every builder must pass it — [`buildFundingTx`](js/otc-engine.js), [`buildClaimTxFromFunding`](js/otc-engine.js), [`buildRefundTxFromFunding`](js/otc-engine.js), `coinjs.addUnspent()` and the manual input rows in [`js/coinbin.js`](js/coinbin.js) all do. `scriptCode` is resolved through `extractScriptKey()`, so it stays correct after signatures have been applied to a multisig input (the raw `ins[i].script` is the scriptSig by then, not the redeem script). The mock in [`tests/harness/mock-infra.js`](tests/harness/mock-infra.js) verifies BCH with bitcoinjs-lib's `hashForWitnessV0` and REQUIRES hashtype 0x41 — an independent implementation, which is the only reason the green BCH suites mean anything. Do not relax that check to make a test pass.
